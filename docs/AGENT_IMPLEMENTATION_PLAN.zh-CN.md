# MatchLens：从交互原型到比赛解读 Agent

> 历史规划，已由 [纯 Harness、按需多 Agent 实施方案](HARNESS_PLAN.zh-CN.md) 取代。下文的固定两个 Agent 和“数据尚未创建”等状态已过时，保留仅供查看早期设计。当前已生成三份事件流、实现查询工具与可配置多角色运行骨架，并接通 DeepSeek Flash；前端连接仍待完成。

规划日期：2026-10-27，北京时间。本文是实施建议，不表示后端或模型已经接入。本轮不修改页面与业务代码。

## 产品要解决的问题

赛事制作人员面对连续事件流，需要及时判断哪些变化值得讲、依据是什么、应该如何向不同观众解释。普通球迷关心“为什么这次机会出现”，分析师需要过程与证据，关注某名球员的观众需要看到他的实际贡献。

MatchLens 的核心能力应是：持续观察比赛，主动调查重要变化，形成有证据的解读，再生成适合不同观众的同步叠加内容与自动回顾。Pocket Stadium 负责把这些结果呈现出来。

## 现有能力与缺口

| 环节 | 当前状态 | 下一阶段要完成 |
| --- | --- | --- |
| Ingest | 浏览器读取三段预置场景 | 服务端按事件时间持续接收、去重、维护当前可见事件边界 |
| Interpret | 计数、坐标插值和预设演变 | 可重复计算的指标与观察窗口；从原始事件发现候选变化 |
| Explain | `phases` 中写好的解说 | Agent 自选工具调查，引用证据，必要时修正或暂不输出 |
| Render | 2.5D 球场、卡片、网格已经可用 | 接收带时间、有效期、证据的结构化后端输出 |
| Personalize | 两套脚本和按身份保存布局 | 按角色、语言、球队、球员改变内容选择、深度和回顾 |
| Recap | 没有自动比赛回顾 | 从已审核的故事记录生成可追溯摘要 |
| Evaluation | 渲染和回放测试 | 未见场景、反例、无依据断言、延迟和失败恢复评测 |

现有 `matches.js` 的 `label`、事件描述和 `phases` 已经包含解释，不能直接当作 Agent 的原始输入。完整未来轨迹也不能提前暴露。演示脚本保留为单独的回归基线。

## 推荐结构：两个 Agent，共享事实与故事记录

### 1. Match Analyst：调查比赛变化

输入：当前事件游标、有限窗口摘要、程序检测到的候选信号，以及可用工具。

工具：

- `query_events(match_id, start, end)`：查看已经发生的事件。
- `compare_windows(metric, before, after)`：比较不同时段的变化。
- `get_player_context(player_id, window)`：查询球员贡献和已有位置采样。
- `calculate_metric(name, filters)`：获取程序计算的指标及对应事件。

Agent 自主决定查哪个窗口、追查哪个球员、是否需要补充位置证据，以及这次变化是否值得生成故事。输出结构化解释候选，分开标注事实、推断和缺失信息；可返回 `ignore` 或 `insufficient_evidence`。

### 2. Broadcast Editor：审核并面向观众编排

输入：Analyst 的解释候选、对应证据、已发布故事记录和观众偏好。

职责：检查叙述是否超过证据，决定发布、退回补查或暂不发布；选择当前观众最相关的信息，生成 Fan / Analyst、中英双语版本和片段回顾。

Editor 可以调用原始证据查询和数值检查工具。退回时说明缺失证据或具体矛盾；最多允许一次补查修订。第二次仍不通过就省略该推断，并显示可确认的事实。

两个 Agent 可以共用同一个模型服务，不需要部署两套模型。各自拥有独立指令、上下文和输出契约。系统保存的是工具调用、事件引用、审核结果和耗时，不展示或编造模型内部思考过程。

### 程序承担的职责

- 事件接收、去重、排序和状态归约；首版先支持固定重放，明确迟到事件处理策略。
- 传球次数、成功率、距离、推进、夺回位置、夺回后多久形成射门等可计算指标。
- 候选信号触发和重复故事抑制，避免每来一个事件都调用模型。
- JSON 类型校验、数字复算、证据引用存在性、未来事件隔离、输出有效期检查。
- 回放时钟、图层定位、字幕同步、界面刷新。

数字检查不能证明战术解释一定正确；Editor 的语义审核也需要通过独立测试验证。首版不输出未经校准的“可信度 98%”。

## 数据流与输出

```text
合成事件流 → 当前比赛状态与程序指标 → 候选变化
                                      ↓
                     Match Analyst ⇄ 比赛查询工具
                                      ↓
                      Broadcast Editor ⇄ 补查/修订
                                      ↓
                 输出校验 → 已审核故事记录 → 个性化输出
                                      ↓
                       SSE → Pocket Stadium / 自动回顾
```

所有查询都绑定同一个 `as_of_event_id` 或状态版本。模型运行期间继续接收新事件；完成时检查结果是否过期。回放跳转时取消或丢弃旧游标的结果，避免上一时刻的解说覆盖当前比赛。

第一版输出至少包含：`insight_id`、`match_id`、`as_of_event_id`、`claims`、`evidence_ids`、`audience`、`language`、`focus`、`display_at`、`expires_at`、`overlays`。图层使用与事件一致的球场坐标；前端不靠故事编号选择预写答案。

## 数据设计与范围

原始记录包含事件 ID、比赛 ID、事件时间、接收时间、半场、球队、球员、事件类型、位置、结果和比赛元数据。明确坐标单位与进攻方向。需要分析阵型、跑位或压迫时，另外提供带采样时间的全员位置；缺少这些数据时只说明事件层面的事实。

第一个场景采用“连续压迫—对手回传—前场夺回—形成射门”。准备三种独立版本：

1. 成功：压迫后夺回球并形成射门。
2. 反例：同样有回传，但对手随后突破压迫，没有前场夺回。
3. 信息不足：删除关键位置或压力记录，要求系统降低结论强度。

随后扩展到快速反击和换人后的阵型变化。换人前后对比只能说明观察到的变化；除非有额外依据，不把“发生在换人之后”说成“由换人导致”。

为展示连续观察，应让关键片段置于一段包含普通传球、失败进攻和无显著变化时段的合成流中。Agent 不知道场景类别、预定高光时刻或最终比分。测试标签只供离线评测。

合成数据先满足比赛一致性：球员数量、换人身份、控球转换、比分更新、事件顺序、传球起终点和合理移动速度。统计展示从数据计算，避免把生成器设定的答案重新包装成推理结果。

## 个性化的具体变化

| 偏好 | 系统行为 |
| --- | --- |
| 普通球迷 | 一句话解释、较少术语、只推送高价值时刻 |
| 分析师/教练 | 时间窗口对比、战术推断边界、数值与事件证据 |
| 关注球队 | 优先该队有球和无球的变化，同时保留必要比赛上下文 |
| 关注球员 | 查询和突出该球员的参与、无球移动与相关片段，不凭号码生成赞美 |
| 中文/英文 | 对同一组审核事实生成不同语言；数字与实体身份保持一致 |
| 片段/比赛回顾 | 从已审核故事记录选择关键节点，附时间与事件引用 |

## 技术路线

建议使用 Python 服务 + Microsoft Agent Framework + Ollama 本地模型服务 + SQLite 事件/故事记录 + SSE。保留当前前端作为独立渲染器。

Microsoft 官方提供 Agent Framework 接入 Ollama、函数工具和流式输出的方式，本地开发无需先建立 Foundry 项目。函数调用是否可靠仍取决于具体模型：[官方 Ollama 集成文档](https://learn.microsoft.com/en-us/agent-framework/integrations/by-component/model-providers/ollama)。

模型先通过小规模工具调用、结构化输出和中英表达测试再选择。需要确认实际可用机器、内存/显存和推理速度；暂不承诺具体模型规模或延迟。首版不进行训练或微调。工具先用普通函数接入，MCP 封装列为后续扩展。

框架负责有界工作流、共享状态和交接；软件函数负责明确的计算任务。这也符合 [Agent Framework 的 agent/workflow 使用建议](https://learn.microsoft.com/en-us/agent-framework/overview/)。

类别建议优先考虑多 Agent 协作方向。须用实际工具调用、退回修订、失败恢复和对照结果证明收益，不能仅用 Agent 数量作为创新依据。暂不主攻需要额外云端建设的 Foundry 或 Azure 云原生类别。

## 下一步：先交付一条真实闭环

第一个里程碑的验收方式：向后台输入一段此前没展示过的压迫事件，Analyst 自主查询窗口与球员上下文，Editor 检查解释，前端显示生成的两类解读和证据。修改数据后，结论随之改变。

建议按以下顺序推进：

1. 确认可用推理资源，启动一个模型端点；用 Agent Framework 做一次真实函数调用和结构化返回测试。
2. 将压迫场景转换为不含解释标签的事件 JSONL，建立成功、失败、信息不足三个版本。
3. 实现事件状态与四个查询/计算工具；单测确保查询看不到未来。
4. 接入 Analyst 与 Editor，记录真实调用与审核结果。先在终端完成；不新增页面设计。
5. 输出统一 insight JSON，经 SSE 替换前端当前预写解说和预设图层触发。明确 Live Agent 与脚本回放状态。

首批建议产物：`backend/schema.py`、`backend/replay.py`、`backend/tools.py`、`backend/agents.py`、三份 `data/fixtures/*.jsonl`、`evals/test_agent_flow.py`。这些路径尚未创建，是后续实施清单。

## 验收与对照

- 未见输入：球员编号、时间、动作顺序改变后仍能分析，不依赖固定句子或场景标签。
- 数值一致：输出中的数字可复算，事件引用全部存在且不晚于当前游标。
- 反例识别：发生回传但未夺回时，不输出“高位压迫成功夺回”；没有进球时不说进球。
- 证据不足：删除支持材料后，系统能降级为事实描述或不输出。
- 个性化：更改关注球员，内容选择发生合理变化；两种语言中的事实一致。
- 失败恢复：模型超时、无效 JSON、缺失工具结果、重复事件不会卡住比赛；退化输出注明为基础事实模式。
- 时间表现：分别测量事件到状态、候选到审核洞察的 p50/p95，以及调用数、token 数、降级比例。先实测再设定发布预算；实时动画不等待模型。
- 多 Agent 收益：用相同模型与相同未见事件，比较单 Agent 基线和 Analyst + Editor 的无依据断言、数值错误、关键时刻覆盖率、延迟及成本。记录真实结果，即使多 Agent 没有全面胜出。

首轮建立至少 12 个正/反/缺失案例，闭环稳定后扩展到约 24 个。测试样本和判断标准随仓库发布，演示案例与评测案例分开。

## 剩余时间的实施顺序

截至本次规划，官方仓库的截止时间换算为北京时间 2026-10-28 14:59：[官方规则](https://raw.githubusercontent.com/microsoft/insidethegamehackathon/main/OFFICIAL%20RULES.md)。以下是约 35 小时窗口内的工作分配建议，不是完成时间保证。

| 相对时间 | 重点 | 完成条件 |
| --- | --- | --- |
| 0–2 小时 | 数据契约、模型通路、测试用例 | 真工具调用成功，正反输入分开 |
| 2–8 小时 | 压迫场景完整闭环 | 输入流 → 两 Agent → 证据 → 现有页面 |
| 8–16 小时 | 扩展反击、换人与失败恢复 | 三类场景可泛化，时间线与洞察同步 |

| 22–28 小时 | 对照评测、可访问测试版本 | 有实测报告，另一环境能运行或访问 |
| 28–33 小时 | 英文材料、公开仓库、约 110 秒录屏 | 演示真实 Agent 闭环，保留提交缓冲 |

评委访问必须覆盖推理服务；只发布静态前端仍不足以体验新的 Agent 能力。需要尽早确定托管服务或可复现测试版本的交付路径。发布、公开仓库和提交在具体材料完成后另行执行。

新的演示重点应是：未见事件输入 → 工具查询 → 证据解读 → 改变输入导致判断改变 → 切换观众 → 自动回顾。现有 120 秒视觉 walkthrough 不能直接作为最终参赛视频；最终目标控制在约 110 秒，留出片头片尾与编码时长余量。

## 首版边界

优先完成事件智能、解释、内容个性化和回顾。视频自动识别、声音克隆、模型训练、全场精确追踪、复杂云基础设施和进一步美术迭代暂不纳入本轮实现。需要球速、射速或距离时，先确认数据具有相应时间与空间精度；没有足够输入就不展示该指标。
