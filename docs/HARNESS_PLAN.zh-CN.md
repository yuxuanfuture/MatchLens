# MatchLens：纯 Harness、按需多 Agent

更新日期：2026-10-27。此方案取代此前固定 Analyst → Editor 的实施建议。项目采用现成模型推理，不训练、不微调，也不更新模型权重。合成数据用于产品输入和评测；下载开源模型用于推理，两者均不属于训练。

## 我们实际要解决的问题

从连续足球事件中主动发现值得解释的变化，查清依据，判断结论是否超出证据，再面向球迷、教练或解说员生成不同深度的内容。真正需要展示的能力包括：反例出现时改变判断，数据不足时缩小结论，复核失败时补查或不发布。

暖色体素球场承接这些结果。关键帧、数字和文案需要由当前观察结果驱动，不能用场景编号选择事先写好的结论。

## Harness 与 Agent 数量

Harness 是包围现成模型的执行系统：提供工具、组织上下文、管理状态和交接、限制时间及调用次数、检查输出、处理失败并保留可审查的运行记录。它与多 Agent 完全兼容。

当前注册六种角色，可通过角色表扩展。它们可共用同一个模型服务，拥有独立任务与对话上下文；不需要下载六份模型。

| 角色 | 何时参与 | 产物 |
| --- | --- | --- |
| Coordinator 协调员 | 每次调查 | 选择调查方向，按需委派，整合结果或放弃发布 |
| Scout 观察员 | 需要筛选重要变化时 | 候选时刻及值得追查的问题 |
| Tactics 战术分析员 | 需要空间、节奏或控球链分析时 | 事实、战术推断及其边界 |
| Verifier 证据复核员 | 每份有内容的发布候选；也可提前咨询 | 针对当前版本的通过或具体退回意见 |
| Audience 观众编排员 | 偏好、语言或表达深度需要专门处理时 | 保持事实一致的 Fan / Analyst 表达 |
| Recap 回顾员 | 用户请求片段回顾时 | 当前可见区间的可追溯摘要 |

不是每个事件都需要调用六个角色。普通输入可忽略；复杂时刻可请多个角色调查。首版的委派执行是串行的，不声称已实现并行调度。只有协调员能委派，防止角色无限递归；所有角色共享一份全局预算。

```text
合成事件流 → 冻结的当前观察 → Coordinator
                                ↕ 查询工具 / 计算指标 / 共享证据
                                ↕ 按需 Scout、Tactics、Audience、Recap
                              发布候选
                                ↓
                       Verifier 检查当前版本
                         ↙退回一次       ↘通过
                    补查与修订         结构化洞察
                         ↓                  ↓
                  仍失败则降级       SSE 接入现有页面
```

## 已实现的部分

| 部件 | 当前实现 |
| --- | --- |
| 三版本数据 | 3 份各 90 秒的 JSONL：压迫后夺回射门、对手脱压迫、关键通道缺失 |
| 生成与一致性校验 | 可复现 seed/hash，22 人、传球落点、控球链、位置和速度检查 |
| 观察隔离 | 同时按事件时间和到达时间过滤；工具不能查询未来或推进时钟 |
| 确定性工具 | 比赛状态、事件查询、球员上下文、指标计算、窗口比较、证据查询 |
| Agent 循环 | 模型选择查询、委派或结束；独立角色上下文与共享事实/报告 |
| 输出控制 | 结构检查、证据 ID 与已计算事实 ID 检查、逐稿复核、一次退回修订 |
| 失败处理 | 模型异常、预算耗尽、重复复核失败时输出 `basic_facts_only`，不发布未通过的叙述 |
| 记录 | 工具参数/结果、角色交接、发布候选、审核意见、调用数和耗时 |
| 模型适配器 | 已接通官方 `deepseek-flash` API，另保留 Ollama 适配器；真实调用记录见独立报告 |

当前已补上持续事件接入、SSE、独立播放会话、SQLite 故事记录、前端输出替换、偏好变更、过期结果丢弃和截至当前时刻/全场回顾。详细结果见 [离线验收报告](OFFLINE_ACCEPTANCE.zh-CN.md)。

当前默认运行 **offline_facts**，不调用任何模型。离线文案依据事件和计算结果生成，不按 stream 文件编号选择答案；页面清楚显示其来源。真实 Agent 仍由已有 Harness 执行，但模型适配器在每次请求前读取独立授权策略。

## 运行方式与授权

```bash
python3 -m backend.server --port 43128
python3 scripts/run_harness.py data/streams/stream-01.jsonl --as-of-ms 68000 --output run-output/offline.json
python3 scripts/validate_match_fixtures.py
python3 -m unittest discover -s tests -p 'test_*.py'
node --test tests/*.test.mjs
```

`config/model-policy.json` 当前 `enabled=false`、预算为 0；旧密钥的哈希进入拒绝列表。`.env.local` 中已清空密钥。页面不能解锁、提交密钥或修改该策略。**只有用户再次明确授权并提供另一个凭证，才可配置真实模型调用。** Ollama 推理也受同一授权门控制，不作为绕过方式。

已具备的模型路径：运行时按 15 秒观察桶调度协调员，共享冻结快照，经独立 Verifier 批准后将结果送给同一 SSE 前端。每个会话同一时间只调查一次。时间线或偏好变更使旧结果失效；超过 30 秒比赛时间的结果不发布。播放 60× 时模型容易过期，因此真实推理演示应从 1× 开始，待授权后测量延迟。此处的 30 秒是发布有效期，不是响应速度承诺。

协议仍是 `tool / delegate / final` JSON action，支持 DeepSeek 与 Ollama 适配器，不依赖训练。新增比赛洞察、球员指标、传球质量、速度工具可注册计算事实。不得将历史真实调用的质量或延迟当作当前连续运行版本的验收结果。

## 数字、证据与失败边界

- 统计由 Python 计算，模型引用 `fact_id`。缺失位置、压力等输入会产生 `null` 与 `insufficient_data`。
- `calculate_metrics` 支持一次计算 1–8 项指标；重复指标复用事实 ID。工具返回每个指标实际依赖的通道覆盖，避免把位置缺失误认为所有事件都缺失。
- 球队工具状态明确己方/对方球门位置；传球和带球带有程序计算的球队视角推进距离与方向，避免模型把所有 x 增大都理解为向前。
- 工具同时区分朝球门的 x 位移与实际起终点距离，不能将两者混写。默认调查窗口为当前观察时刻之前的 30 秒，允许补查更早上下文，但短窗口计数不能冒充整个片段的计数。
- 文案检查限制片段统计冒充全场统计、仅凭 recovery 事件声称抢断，以及将因果判断标为直接观察。否定或限制性说明不被当作全场统计断言。这些检查只覆盖有限表达形式，语义复核仍需独立评测。
- 输出将观察、推断、限制分开。每项陈述需要可见事件引用或已计算事实引用。
- 引用存在性检查不等于自然语言真实性证明。Verifier 还要检查文案与数字是否一致、战术解释是否过强；其判断同样需要评测，不能把模型复核当作准确率保证。
- 一个调查中的所有角色使用同一时间快照。运行时已经丢弃过期结果，并用观察版本号拒绝时间线/偏好变化前的调查结果。
- 默认开发预算为 24 次模型调用、36 次工具调用、每角色 10 轮、单请求 30 秒和总计 120 秒。它们是防止失控的上限，不是直播延迟承诺。接入真实模型后应测量延迟并收紧预算。
- Trace 记录外部动作和证据，不记录或展示模型的私有思考过程。测试替身只出现在测试文件中，不提供“模拟 Agent 在线”的产品模式。
- 模型已响应但 JSON 为空或不合法时，每个角色最多重试一次，计入同一总预算；认证、余额和网络错误不会被当作格式问题反复请求。窗口或事件类型的文案检查允许明确的否定说明，例如“不能代表全场”和“无法确认是否通过抢断”。

## Microsoft 技术接入

纯 Harness 表示通过推理时的工具和编排解决问题，可以采用 Microsoft Agent Framework。官方框架支持 Agent、工具、工作流及 Ollama 等模型提供方：[Agent Framework 概览](https://learn.microsoft.com/en-us/agent-framework/overview/)。

当前实现是便于检查数据边界的独立 Python 核心，尚未集成该 SDK。参赛下一阶段建议把模型/角色执行接入 Agent Framework，继续复用事件工具、证据契约与评测，不需要先训练或创建 Foundry 项目。具体本地集成方式以[官方 Ollama 文档](https://learn.microsoft.com/en-us/agent-framework/integrations/by-component/model-providers/ollama)为准。

参赛材料必须如实说明实际使用的 Microsoft 技术；当前独立 Harness 不能写成“已集成 Microsoft Agent Framework”。此前规则要求至少符合一个类别，且技术评分考虑 Microsoft 重点技术；多 Agent 类别也关注有作用的分工、交接、失败恢复和相对单 Agent 的收益。见仓库上一级保存的完整官方规则第 4.2、7 节。

## 下一步的具体顺序

1. **模型端点已接通。** 使用 `deepseek-flash` 做真实工具查询和复核；不进行训练或微调。
2. **用实测继续收敛。** 三版本真实运行与发现的问题见报告；扩展到相同前缀、偏好切换和独立新场景，衡量证据覆盖、误判和延迟。
3. **完成连续观察和 Microsoft 执行层。** 用事件触发调查、保存已审核故事、抑制重复，加入过期检查；用实际运行记录验证框架接入。
4. **把结果接到现有页面。** 文案、战术格子和证据卡均读取同一份结构化洞察；Fan 与 Analyst 使用同一事实，不同表达和细节。
5. **补充独立变化与对照。** 新增不同球员、位置、动作顺序和结局；比较仅协调/复核与按需更多角色的质量、延迟及调用成本。合成器的简单 seed 偏移不算独立泛化样本。

首个完整验收应是：换一份输入，系统自主查询，发现结论需要改变，复核后在页面显示变化及依据。约 110 秒的最终视频应演示这个闭环，再演示偏好切换和片段回顾。数据本身无需只有两分钟，也无需取自同一场真实比赛视频。
